## D-4. GitHub 레포는 프라이빗 (하이브리드)

**결정일** 2026-08-15 (운영자가 복제 우려 제기 후 재검토)
**결정** 측정 엔진은 프라이빗 레포. 산출 데이터와 웹사이트는 공개.

**검증 결과**
| 플랜 | 프라이빗 Actions 무료 시간 |
|---|---|
| **Free (기본 전제)** | **2,000분/월** |
| Pro (학생팩 승인 시) | 3,000분/월 |
| 퍼블릭 | 무제한 |

100개 서비스 일 1회 측정 ≈ 회당 20분 → **월 600분 추정**. **Free 플랜만으로 3배 여유.**
300개·일 3회로 늘려도 3,000분 안쪽(이 경우 Pro 필요).
학생팩은 보너스이지 전제 조건이 아님 — 승인 여부와 무관하게 진행.
Vercel Hobby는 프라이빗 레포와 연결 가능, Cloudflare Workers는 레포 무관.
→ **퍼블릭을 강제하는 요소가 없음.**

**근거**
- 코드는 해자가 아님. Playwright + Next.js 정적 사이트는 AI 도구로 일주일이면 재작성 가능
- 진짜 자산: ① 축적된 시계열(복제자는 스냅샷만 얻고 0일차부터 시작, 과거는 소급 생성 불가) ② 제보자 커뮤니티 ③ 인용 위치 ④ 도메인·백링크
- **데이터 공개는 엔진 공개와 무관.** 데이터가 열려야 AI가 인용하고 기관이 봄
- **순서가 중요**: 프라이빗→퍼블릭은 언제든 가능, 퍼블릭→프라이빗은 불가능. 되돌릴 수 없는 결정은 뒤로 미룸

**데이터 라이선스** CC BY (출처 표시 조건). 법적 집행보다 평판 보호 목적.

**재검토 시점** 시계열 자산이 6개월 이상 쌓인 뒤, 오픈소스 공개의 포트폴리오 이득과 비교.

## D-8. 측정할 수 없는 것은 측정하지 않는다 (1주차 구현 중 확정)

**결정일** 2026-08-15 (1주차 프로브 구현·검증 중)

명세(`02-product-spec.md` 4장)와 실제 측정 가능 범위가 어긋나는 지점이 3곳 나왔다.
전부 **추측으로 채우지 않고 측정 범위를 좁히는 쪽**으로 결정했다. 근거는 절대규칙 5.

### D-8-1. `app_availability` — 국가별 출시 여부는 측정하지 않는다

**검증 결과** 세 가지 공개 경로를 모두 시험했으나 어느 것도 배포 국가를 구분하지 못했다.

| 방법 | 결과 |
|---|---|
| `itunes.apple.com/lookup?country=XX` | 정부24·KB스타뱅킹도 us/de/jp에서 `resultCount=1` |
| `apps.apple.com/{cc}/app/id{id}` | 모든 국가 200 (없는 앱만 404) |
| `play.google.com/...&gl={cc}` | 모든 국가 200 (없는 패키지만 404) |

**결정** `countries` 는 항상 `null` 로 두고, 실제로 검증되는 **스토어 등재 여부**만 측정한다.
등재 여부 자체도 정보 가치가 있다(외국인이 앱 이름으로 못 찾는 경우가 흔하다).
부수 효과로 요청 수가 서비스당 28회 → 2회로 줄어 실행 시간이 크게 짧아졌다.

**재검토 시점** 국가별 측정 방법이 확인되면 `src/probes/app-availability.ts` 만 교체한다.

### D-8-2. `overseas_access` — 봇 차단과 지역 차단을 구분할 수 없으면 `unknown`

**문제** 쿠팡 등은 봇 User-Agent를 403으로 막는다. 이걸 "해외에서 차단됨"으로 발표하면
**사실이 아니고**, 기업 항의에 정당한 빌미를 준다 (리스크 표의 "우리 사이트를 그렇게 표시하지 말라" 항목).

**결정** `blocked` 로 단정하는 조건을 좁혔다.
- `blocked`: 본문이 지역·국가 제한을 **명시**하거나 HTTP 451
- `unknown`: 403/429, 또는 "Access Denied" 류의 사유 불명 거부 → 근거를 evidence에 남기고 판정 보류
- `ok`: 2xx/3xx 정상 응답 / `degraded`: 5xx

봇 차단 여부는 실제 브라우저 접속 제보로만 확정 가능하므로 커뮤니티 제보 항목으로 넘긴다.

### D-8-3. 차단·오류 페이지를 측정 근거로 쓰지 않는다

`i18n_ui` 와 `payment_gate` 가 403 차단 페이지를 그대로 분석해
"이 서비스는 한국어만 제공", "PG 없음" 같은 **틀린 값**을 만들어내고 있었다.
두 프로브 모두 2xx/3xx 응답을 받았을 때만 측정하도록 고쳤다. 아니면 `unknown`.

## D-9. robots.txt가 자동 측정의 상한이다 (1주차 실측)

**실측** 시드 106개 중 **28건(26%)이 자동 측정 불가**였다.

| 사유 | 건수 | 예 |
|---|---|---|
| robots.txt `Disallow: /` | 약 22건 | 네이버쇼핑·네이버예약, 카카오선물하기·카카오뱅크, 인터파크, 무신사, 멜론, 11번가, 롯데온 |
| 봇 UA를 403으로 차단 | 약 7건 | 쿠팡, G마켓, 옥션, CGV, 올리브영 |

검증해 보니 이 사이트들은 Googlebot·Applebot 등 **지정 봇만 화이트리스트**로 허용하고
`User-agent: *` 에는 전면 금지를 건다. 우리 봇은 정확히 그 대상이다.

**결정** robots.txt를 우회하지 않는다. 크롤링 정당성 유지가 프로젝트 생존 조건이므로(D-6),
이 26%는 **커뮤니티 제보로만 채우는 영역**으로 확정한다.

**함의 (제품 설계에 반영할 것)**
- 3주차 제보 레이어는 "봇이 못 하는 것을 보완"이 아니라 **주요 서비스 상당수의 유일한 데이터원**이다.
  우선순위를 높게 볼 것.
- 사이트에 "이 서비스는 robots.txt로 자동 측정을 금지하고 있어 제보로만 채웁니다"를 명시한다.
  이것 자체가 정직성의 근거이자 제보 유도 장치다.

## D-10. 가입 본인인증 판정 — "무엇을 봤는지"까지 확인한 뒤에만 값을 낸다

**결정일** 2026-08-15 (운영자가 1등급 33건의 가입 주소를 제공한 직후, 실측 검증 중)

운영자가 채워 준 주소로 처음 측정했을 때 **양방향 오류가 실제로 발생**했다.

| 사례 | 잘못된 결과 | 원인 |
|---|---|---|
| KT `accounts.kt.com/identify/personal` | `not_required` | 페이지에 "본인확인… 주민등록번호 앞 7자리… PASS 또는 아이핀으로 인증하기"가 그대로 있는데, 시그니처 사전에 `본인확인`·`아이핀`·`인증번호`가 없어 못 잡음 |
| 신한은행 회원가입**안내** 페이지 | `not_required` → (사전 보강 후) `required` | 입력 양식이 아니라 안내 문서였다. 위젯이 없는 게 당연한데 "불필요"로 발표할 뻔했고, 반대로 안내문의 "주민등록번호" 언급만으로 "필수"로 발표할 뻔했다 |
| 쿠팡 `login.coupang.com` | `not_required` | 가입이 아니라 로그인 화면이었다 |

**결정** 값을 내기 전에 두 가지를 함께 확인한다.

1. **페이지 종류** (`src/lib/page-kind.ts`) — 가입 관련 표시가 없고 로그인 표시만 있으면 판정하지 않는다.
   로그인 절차를 재고 가입이라고 발표하면 잰 것과 발표한 것이 달라진다.
2. **입력 양식 존재** — 사람이 채우는 입력칸이 2개 이상 있어야 한다.
   - 입력칸 없음 → `unknown` ("안내 페이지로 보임")
   - 입력칸 있음 + 시그니처 없음 → `not_required`
   - URL 시그니처 탐지, 또는 텍스트 시그니처 + 입력 양식 → `required` / `optional`

즉 **텍스트 문구만으로는 required 를 발표하지 않는다.** 위젯 URL이 잡히거나,
문구와 실제 입력 양식이 함께 있어야 한다. evidence에 `page_kind`와 `form_input_count`를 남겨
왜 그렇게 판정했는지 외부에서 반증할 수 있게 한다.

**부수 결정** 시그니처 사전에 `본인확인`, `아이핀/i-PIN`, `인증번호 받기`, `주민등록번호`,
`외국인등록번호` 등을 추가했다 (`data/signatures/identity-verification.json`).
`주민등록번호` 요구는 외국인에게 특히 중요한 신호라 별도 항목으로 분리했다.

**알려진 한계** 해시 라우팅 기반 SPA(예: 신한은행)는 실행 시점에 따라 렌더링 결과가 달라져
값이 흔들릴 수 있다. `/changes` 에 가짜 변경으로 잡힐 여지가 있으므로, 2주차에
"연속 2회 같은 값일 때만 변경으로 인정" 같은 안정화 장치를 검토할 것.

## D-11. 공개 사이트는 `site/` 안의 정적 사이트로 분리한다

**결정일** 2026-08-15 (2주차 시작)

측정 엔진과 사이트를 한 폴더에 섞는 방법도 있었으나 그렇게 하지 않았다.

**결정** `site/` 에 Next.js 프로젝트를 따로 두고, `output: 'export'` 로 **순수 HTML/JS만** 뽑는다.
사이트는 빌드 시점에 `../data` 를 파일로 읽고, 런타임에는 아무것도 읽지 않는다.

**이유**
- **서버 0대 원칙 유지.** 결과물이 정적 파일이라 Vercel Hobby·GitHub Pages·S3 어디에 올려도
  동작하고 런타임 비용이 0이다. 트래픽이 늘어도 요금이 늘지 않는다.
- **엔진과 사이트의 tsconfig가 다르다.** 엔진은 `NodeNext`(import에 `.js` 확장자 필요),
  사이트는 `bundler` 다. 한 폴더에 섞으면 둘 중 하나가 환경에 따라 깨진다.
- **의존성 격리.** 사이트가 죽어도 크론은 계속 돈다. 반대도 마찬가지다.

**부수 결정**
- 타입은 `site/lib/types.ts` 에 **사본**을 둔다. 폴더를 가로지르는 import 는 모듈 해석 방식이
  달라 빌드가 환경 의존적으로 깨진다. 사이트는 데이터를 읽기만 하므로 사본이 안전하다.
  원본은 `schema/service.schema.json` 이고, 데이터 쪽 어긋남은 `npm run check` 가 잡는다.
- 공개 JSON API 는 `site/scripts/build-api.mjs` 가 빌드 전에 `site/public/api/v1/` 로 생성한다.
  **커밋하지 않는다** — `data/` 에서 파생된 것이라 커밋하면 같은 사실이 두 곳에 저장된다.
- `validate` 워크플로에 사이트 빌드 잡을 추가했다. 데이터 모양이 바뀌면 여기서 먼저 깨진다.

## D-12. 화면 규칙 — "모른다"를 실패처럼 보이게 하지 않는다

**결정일** 2026-08-15 (2주차, 첫 화면을 실제로 띄워 보고)

848칸 중 값이 있는 것은 278칸(33%)이다. 처음 만든 화면은 첫 스크롤이 온통
"not measured" 회색 벽이라, **데이터가 없는 사이트로 오해되는** 문제가 있었다.

값을 감추거나 빈칸을 지우는 선택지는 버렸다 — 그건 이 제품의 존재 이유를 버리는 것이다.
대신 **표현 규칙** 세 가지를 정했다.

1. **"측정 안 됨"은 점선 + 회색으로 그린다.** 실패나 결함이 아니라 *일부러 비워둔 칸*으로 읽혀야 한다.
   그리고 **왜 비었는지를 값 자리에 함께 쓴다** (robots.txt / 봇 차단 / 주소 미상 / 근거 부족 /
   제보 대기). 이유 없는 빈칸은 낡은 정보와 구분되지 않는다.

2. **색은 좋다·나쁘다가 아니라 "외국인 앞에 장벽이 있는가"만 나타낸다.**
   이 사이트가 던지는 질문 자체가 그것이므로 사실 기술의 범위 안에 있다 (절대규칙 6).
   색만으로 의미를 전달하지 않고 항상 텍스트를 함께 낸다.

3. **기본 정렬은 중요도 → 기록된 값 개수 순.** 전부 목록에 있고 필터로 골라볼 수 있으므로
   감추는 것이 아니다. 첫 화면이 빈칸 벽이면 "이 사이트에는 데이터가 없다"는 잘못된 인상을 주고,
   그건 실제 커버리지(33%)보다 더 부정확한 전달이다. 커버리지 막대와 차단 서비스 수는
   홈 화면에 그대로 내건다.

**부수 결정** 값이 있어도 오해를 부르는 두 경우에는 값 옆에 단서를 붙인다.
- `payment_gate` 가 비었을 때 → "공개 페이지에서 탐지되지 않음"이지 "결제사가 없음"이 아니다
- `signup_phone_auth` 가 `not_required` 일 때 → 양식을 읽었을 뿐 제출하지 않았으므로,
  제출 후에 나타나는 인증 단계는 보이지 않는다

## D-13. Vercel 배포는 `vercel.json` 으로 고정한다 (Root Directory 를 쓰지 않는다)

**결정일** 2026-08-15 (2주차 배포 시도 중, 실제로 막혀서)

`site/` 를 푸시하고 Vercel에서 Import 했는데 **Root Directory 폴더 목록에 `site` 가 나타나지 않았다.**
페이지 새로고침·프로젝트 재생성 모두 소용없었다. GitHub 서버에는 확실히 있었다:

```
$ git ls-remote origin refs/heads/main
aadd005a...  refs/heads/main
$ git ls-tree --name-only origin/main
.github  data  docs  schema  site  src  ...
```

즉 Vercel이 GitHub App 권한을 부여받던 시점의 레포 트리를 캐시하고 있고, 그 캐시가
UI 조작으로는 갱신되지 않는다.

**결정** Root Directory 를 아예 쓰지 않는다. 레포 최상위에 `vercel.json` 을 두고
빌드 명령과 산출 경로를 직접 지정한다. Vercel UI 는 기본값 그대로 두고 Deploy 만 누른다.

**이 방식이 없앤 문제 2가지**
1. **캐시된 폴더 목록** — 고를 필요가 없으니 목록이 낡았든 말든 상관없다.
2. **"Include files outside of the Root Directory" 체크박스** — Root Directory 를 `site` 로 잡으면
   기본값이 꺼져 있어 상위 폴더가 빌드에서 제외되고, 사이트가 읽는 `../data` 가 통째로 사라진다.
   Root 가 레포 최상위면 애초에 생기지 않는 문제다.

**부수 효과** `installCommand` 를 명시했으므로 Vercel이 최상위 `package.json`(측정 엔진 —
Playwright 포함)을 설치하려 드는 것도 막힌다. 사이트 빌드에 불필요하고 느리다.

**검증** Vercel이 실행할 명령을 그대로 로컬에서 돌려 확인했다.
`cd site && npm ci` → `cd site && npm run build` → `site/out/` 에 정적 파일 생성 →
정적 서버로 띄워 `/`, `/service/kt/`, `/changes/`, `/method/`, `/api/v1/meta.json` 전부 200.

**운영자용 결론** Vercel 화면에서 **아무것도 설정하지 않는다.** Import 후 Deploy 만 누른다.

## D-14. 해외 측정 첫 실행에서 드러난 것 세 가지

**결정일** 2026-08-15 (GitHub Actions 첫 수동 실행 — US · Washington · AS8075)

측정 지점이 처음으로 한국 밖으로 나갔다. 106/106, 오류 0건, 변경 39건.
그 39건을 들여다보다가 **사이트가 실제로 거짓말을 하고 있는 것**을 발견했다.

### 1. `robots` 라는 낱말로 뭉뚱그려 회사에 없는 죄를 씌우고 있었다 — **버그, 수정함**

엔진은 전혀 다른 두 상황에 모두 `robots` 가 들어간 문자열을 남긴다.

```
"robots: Disallow: /"                          사이트가 크롤러를 금지했다
"robots: robots-unavailable(CONNECT_TIMEOUT)"  robots.txt 를 읽지도 못했다
```

사이트의 `explainMissing` 이 문자열에 `robots` 가 있는지만 봤기 때문에, 티머니 페이지에
이렇게 공개돼 있었다.

> "This site's robots.txt tells automated clients to stay away from this path."

**실제로 일어난 일은 미국 IP에서 22초 동안 연결이 안 된 것이다.** 티머니의 robots.txt는
읽어본 적도 없다. 회사가 하지 않은 의사표시를 했다고 발표한 셈이고, 동시에
**진짜 발견(해외에서 접속 불가)을 덮었다.** 절대규칙 6 위반이다.

`classifyBlock()` 으로 다섯 가지를 구분하도록 고쳤다.

| 구분 | 뜻 | 이번 실행 |
|---|---|---|
| `robots-disallow` | 사이트가 금지 → 우리가 안 간다 | 기존 다수 |
| `bot-block` | 403/429 로 거부당함 | LG U+, 쿠팡이츠 |
| `unreachable` | 연결 자체가 안 됨 | 티머니, 고속버스 |
| `tls` | 인증서 체인 검증 실패 | 서울교통공사 |
| `robots-unreadable` | robots.txt 만 못 읽음 (그 외) | — |

### 2. `/method` 의 주장이 과했다 — **수정함**

원문: *"The default environment of the robot is the same environment a foreign visitor is in."*

**아니다.** GitHub 러너는 데이터센터(Azure, AS8075) IP다. 한국 사이트 상당수가
데이터센터 대역을 VPN·스크래핑으로 보고 가정용 회선과 다르게 취급한다.
직전 한국 실행은 운영자의 가정용 회선(AS9318)이었으므로, 이번 비교는
**국가와 회선 종류를 동시에 바꾼 것**이다. 한 번의 실행으로 둘을 분리할 수 없다.

그래서 6건 전부 `blocked` 가 아니라 **값 없음**으로 남긴다. 어느 쪽이 진짜로 외국인을
막는지는 평범한 회선을 쓰는 현지의 사람만 답할 수 있고, 이것이 3주차 제보 레이어의
가장 강한 논거다.

### 3. 변경 이력에 측정 지점이 없어 39건이 "회사가 바꿈"으로 읽혔다 — **수정함**

`ChangeEntry` 에 `vantage_point` 를 추가했다. 없으면 *"값이 바뀌었다"* 와
*"우리가 다른 곳에서 쟀다"* 를 구분할 수 없다. `/changes` 는 직전 실행과 측정 국가가
다르면 해당 묶음 위에 경고를 띄운다.

**부수 수정** 같은 날 두 번 돌면 변경 파일을 덮어쓰고 있었다. 실제로 이날 첫 실행(KR)의
4건이 사라졌다. 이어붙이도록 고치고, 사라진 4건은 git 히스토리에서 되살렸다.
측정 지점은 `changed_at` 이 각 실행의 `started_at` 과 정확히 일치하므로 기계적으로 붙였다
(추측 아님). 43건 = KR 4 + US 39.

git 로그에 쌓이는 변경 이력이 이 프로젝트의 해자다. 한 건도 버리면 안 된다.

## D-15. 언어 전환 — 두 언어를 다 넣고 CSS로 고른다

**결정일** 2026-08-15 (2주차 UI 개편)

첫 버전은 모든 문구를 영어 + 회색 한국어로 **두 줄씩 쌓아** 보여줬다. 화면을 실제로 띄워 보니
이것이 "기계가 만든 페이지"처럼 보이는 가장 큰 원인이었다. 글자 수가 두 배가 되고 리듬이 죽는다.

**결정** 언어 전환 버튼을 두고 한 번에 한 언어만 보여준다. **기본값은 영어**,
한국어는 사용자가 직접 눌렀을 때만.

**구현 — 왜 이렇게 했나**

정적 사이트라 요청 시점에 언어를 고를 서버가 없다. 흔한 방법인 "마운트 후 상태로 교체"는
한국어 사용자에게 영어가 한 번 번쩍이고, 서버 HTML과 클라이언트 첫 렌더가 달라 hydration 경고가 난다.

그래서 **두 언어를 모두 HTML에 넣고 CSS로 한쪽을 숨긴다.**
- `<head>` 인라인 스크립트가 그리기 전에 `<html data-lang>` 을 정한다 → 깜빡임 없음
- 두 언어가 항상 DOM에 있으므로 hydration 불일치가 원리적으로 불가능
- JS가 꺼져 있어도 영어가 보인다
- `display:none` 이라 스크린리더도 한쪽만 읽는다

비용은 HTML이 본문만큼 커지는 것인데, 이 사이트는 근거 JSON이 본문보다 훨씬 크므로 차이가 없다.

**브라우저 언어를 보지 않는 이유** 한국에 있는 외국인의 브라우저가 한국어로 설정된 경우가
흔해서 자동 감지가 자주 틀린다. 기본은 영어로 고정하고 선택만 기억한다.

**한국어 타이포그래피 두 가지** (라틴 기준 설정을 그대로 쓰면 깨진다)
- `word-break: keep-all` — 없으면 "신분증"이 "신분 / 증"으로 갈라진다
- 제목은 한글만 산세리프로 — 제목용 세리프(Newsreader)에 한글 글리프가 없어 OS 명조로
  떨어지는데 화면에서 낡아 보인다. 굵기와 자간을 조여 세리프와 존재감을 맞춘다

## D-16. 제보 레이어 — 개인정보를 "안 받는다"가 아니라 "받을 곳이 없다"

**결정일** 2026-08-15 (3주차)

시그널 8종 중 2종은 실제 결제·실제 인증 문자 없이 확인할 수 없고 그것은 하지 않기로 한 일이다.
게다가 106개 중 31개는 robots.txt·거부·무응답·인증서로 자동 측정이 원천 불가다 (D-9, D-14).
**그 서비스들에게 제보는 보완이 아니라 유일한 데이터원이다.**

**결정** GitHub Issue Form 으로 받는다. 백엔드·DB·스팸 필터를 GitHub에 위임한다.

**개인정보를 막는 방식 — 3중**
1. **폼에 칸이 없다.** 이름·연락처·전화번호·카드번호를 적을 자리를 만들지 않았다.
   "안 보겠다"는 약속이 아니라 넣을 곳이 없는 구조다.
2. **자유 서술은 저장 전에 검사한다.** 이메일·카드번호·국제전화·한국 휴대폰·주민번호
   패턴에 걸리면 **디스크에 쓰기 전에 본문을 버리고** 제보를 반려한다. 넓게 잡는다 —
   사람이 한 번 더 보는 비용보다 공개 레포에 개인정보가 커밋되는 사고가 비교할 수 없이 크다.
3. **빈 이슈를 막았다** (`blank_issues_enabled: false`). 자유 서식을 열어 두면
   사람들이 이메일·전화번호를 적어 보내게 되고 그 순간 약속이 깨진다.

**엇갈리면 고르지 않는다** 같은 서비스에 상반된 제보가 오면 한쪽을 채택하지 않고
`conflicting` 으로 남긴다. 해외 카드는 발급사·발급국·시점에 따라 갈리는 것이 실제로 정상이라,
하나를 고르는 순간 그것이 거짓이 된다.

**사람 승인 없이는 반영되지 않는다** 워크플로가 PR을 열 뿐 main 에 직접 쓰지 않는다.

**검증** 시험 제보 3건으로 확인했다.
- 정상 제보 → `accepted`, 값 `fails`, 신뢰도 `community`
- 상반된 제보 추가 → 값 `mixed`, 신뢰도 `conflicting` (한쪽을 고르지 않음)
- 이메일·전화번호가 섞인 제보 → `rejected`, **저장된 파일 어디에도 그 문자열이 없음**

**남은 결정 (운영자 몫)** 코드 레포가 프라이빗이라 외부인이 이슈를 열 수 없다.
제보를 받으려면 **공개 레포가 하나 필요하다** — 하이브리드(코드 비공개, 데이터·제보 공개)의
나머지 반쪽이다. 만들고 나서 `NEXT_PUBLIC_ISSUES_REPO` 에 이름을 넣으면 UI가 붙는다.
그전까지 `/report` 는 "준비 중"으로 표시하고 이메일을 안내한다.

## D-17. 제보 창구는 별도 공개 레포. 프라이빗 레포가 그것을 읽어 온다

**결정일** 2026-08-15 (3주차 마무리)

D-16 에서 남겨 둔 결정. 코드 레포는 프라이빗이고(D-3) **프라이빗 레포에는 외부인이 이슈를
열 수 없다.** 그런데 제보는 외부인이 하는 것이다.

**결정** 공개 레포 `works-in-korea-reports` 를 따로 만든다. 제보 폼만 거기 두고,
프라이빗 레포는 그 이슈를 **읽어 온다.**

```
공개 레포  works-in-korea-reports   Issue Form 3종 + README.  이슈가 여기 쌓인다
   │  (공개 레포의 이슈는 인증 없이 읽힌다)
   ▼
프라이빗   report-poll 워크플로 (매일 18:30 UTC, 측정 크론 직후)
           → 이슈 배열을 받아 npm run ingest
           → 개인정보 검사 · 집계 · PR 생성
           → 사람이 승인해야 main 에 들어간다
```

**검토했다가 버린 대안들**
- *전체를 공개로 전환* — D-3 재논의 사항이라 지금 건드리지 않는다.
- *데이터도 공개 레포로 옮기기* — 사이트 빌드가 원격 레포에 의존하게 되고, 양방향 동기화가
  생긴다. 운영자가 디버깅할 수 없는 복잡도다. 데이터는 이미 사이트의 `/api/v1/*.json` 으로
  공개되고 있으므로 공개성 측면의 손실도 없다.
- *공개 레포에서 이벤트로 프라이빗 워크플로 켜기* — 크로스 레포 트리거에는 PAT가 필수다.
  폴링은 토큰 없이 되고, 하루 1회면 충분하다.

**토큰을 선택 사항으로 둔 이유** 공개 레포의 이슈를 **읽는 데는 인증이 필요 없다.**
제보자에게 답글을 다는 것만 쓰기 권한이 필요하다. 그래서 `REPORTS_TOKEN` 이 없으면
답글 단계만 건너뛰고 나머지는 전부 동작한다. 운영자가 토큰 없이 바로 시작할 수 있다.

**개인정보에 대해 정직하게 적어 둘 것** 우리 검사는 제보를 **데이터로 다시 공개하지 않게**
막을 뿐, **이미 공개 이슈에 올라간 본문을 되돌리지는 못한다.** 그래서
- 각 폼 맨 위에 "여기 적는 것은 영구히 공개된다"를 명시했고,
- PR 체크리스트에 "`rejected` 제보가 있으면 공개 레포의 해당 이슈를 **삭제**했는가"를 넣었다.

이건 자동화로 덮을 수 없는 부분이고, 덮는 척하면 안 된다.

## D-18. 오픈소스로 전환 — D-3 뒤집기

**결정일** 2026-08-15 (운영자 결정)

D-3 에서 "복제 우려" 때문에 코드를 비공개로 두고, 자산이 쌓인 뒤 재결정하기로 했다.
운영자가 재결정했다: **공개한다.**

**공개해도 되는 이유 (뒤늦게 분명해진 것)**
- **해자는 코드가 아니라 누적된 측정 이력이다.** 복제자는 코드를 얻어도 0일차에서 시작한다.
  `data/` 의 git 로그에 쌓인 "언제 무엇이 바뀌었는가"는 시간으로만 만들어진다.
- **측정 방법은 이미 전부 공개돼 있었다.** `/method` 페이지, 탐지 시그니처, 원본 근거 JSON,
  크롤러 User-Agent까지. 코드만 감추는 것은 실질적 보호가 아니라 형식이었다.
- **공개가 이 제품의 주장과 일치한다.** "측정을 검증할 수 있게 전부 공개한다"고 말하면서
  측정하는 코드를 감추는 것은 앞뒤가 맞지 않는다.

**라이선스**
- 코드 `MIT` — 최대한 가져다 쓰라는 뜻. 데이터의 CC BY 와 태도가 같다.
- 데이터 `CC BY 4.0` (`LICENSE-DATA`) — 기존 방침 유지.
- AGPL 도 검토했다. 남이 이 코드로 폐쇄형 서비스를 돌리는 것을 막을 수 있지만,
  선의의 재사용까지 막는다. 해자가 코드가 아니라고 판단한 이상 MIT 가 목적에 맞는다.
  마음이 바뀌면 이후 커밋부터 바꿀 수 있다 (이미 배포된 버전은 되돌릴 수 없다).

**공개 전에 실제로 걸러낸 것**
- 커밋 이력 전체에서 API 키·토큰·`.env` 류를 검사했다. **없었다.**
- **`CLAUDE.md` 의 운영자 프로필** — 미성년자의 학년, 월 예산, 가용 시간이 들어 있었다.
  프로젝트를 이해하는 데 필요하지 않으면서 되돌릴 수 없는 노출이라
  `CLAUDE.local.md`(gitignore)로 옮기고, 공개 문서에는 "1인 운영, 법인 없음"만 남겼다.
  **레포를 공개로 돌리는 순간 커밋된 모든 것이 영구히 공개되고 수집된다.**
  앞으로 이 레포의 어떤 파일에도 개인 정보를 적지 말 것.

**공개해도 새로 생기지 않는 위험** 코드가 공개되면 사이트가 우리 크롤러를 더 쉽게 막을 수
있다는 우려가 있으나, UA 와 robots.txt 준수 정책은 이미 공개돼 있어 막고 싶은 사이트는
이미 막을 수 있었다. 우회를 하지 않는 크롤러에게 소스 공개는 추가 위험이 아니다.

## D-19. 빈칸을 메우는 순서 — 원인을 셋으로 갈라서 각각 다르게 푼다

**결정일** 2026-08-15

2주차 사이트를 띄우고 나니 목록 세 번째 열(가입)이 106칸 중 97칸이 비어 있었다.
운영자가 "쓸 만한 상태가 아니다"라고 했고, 맞는 지적이었다.

**원인을 세어 보니 하나가 아니라 셋이었다.** 각각 해결책이 다르므로 섞으면 안 된다.

| 원인 | 건수 | 고칠 수 있나 |
|---|---|---|
| 가입 주소·앱 ID를 우리가 모름 | 121 | **우리 공백. 찾으면 된다** |
| `ANTHROPIC_API_KEY` 미설정 | 74 | **운영자가 키만 넣으면 된다** |
| 사이트가 자동 접근을 막음 | 42 | 영구 불가. 제보만이 유일한 경로 |

셋째만 진짜 벽이고, 앞의 둘은 아직 안 한 일이었다.

**그래서 `npm run find-hints` 를 만들었다.** 규칙은 하나다 — **추측한 값은 쓰지 않는다.**

- **가입 주소** 홈페이지에 실제로 걸린 링크만 따라간다. 연 다음 프로브와 **똑같은 조건**으로
  검사해서, 가입 표시가 있고 입력란이 2개 이상일 때만 기록한다. 로그인 화면이거나
  안내 문서면 후보로만 남기고 사람이 고르게 한다.
- **앱 ID** 세 경로의 근거 강도가 다르므로 등급을 나눴다.
  1. 사이트가 자기 홈페이지에서 스토어를 링크 → **확인**. 서비스 본인의 진술이다.
  2. 아는 안드로이드 패키지로 iTunes 조회 → **확인**. bundleId 정확 일치다.
  3. ~~이름 검색 + 개발사 홈페이지 일치~~ → **쓸 수 없다. 아래 참고.**

**이름 검색을 못 쓰는 이유 — 애플 robots.txt 가 금지한다**

```
Disallow: /search*        검색 금지
Disallow: /*/lookup?      /us/lookup? 같은 형태만 금지. 루트 /lookup? 은 허용
```

그래서 `lookup` 은 되고 `search` 는 안 된다. `politeFetch` 가 이미 이것을 막고 있었고,
앱 후보가 0건으로 나오는 것을 이상하게 여겨 확인하다가 알았다. **코드가 옳게 동작한 것이다.**
우회 코드를 넣지 말 것.

> 확인 과정에서 Claude 가 `curl` 로 이 금지 경로를 130여 회 직접 호출했다. 크롤러가 아니라
> 진단용이었지만 절대규칙 4 위반이다. 애플의 rate limit 에 걸려 중단됐다. 앞으로 탐색 단계에서도
> `politeFetch` 를 쓸 것 — 규칙을 지키는 경로를 두고 우회하면 규칙이 없는 것과 같다.

**금지가 아니었더라도 자동 적용은 못 했다.** 네이버로 검색하면 지도·페이·예약 앱이 전부
`sellerUrl=naver.com` 이라 규칙만으로는 고를 수 없다. 자동 적용했다면 네이버페이에
네이버 앱이, 멜론티켓에 멜론 음악앱이 붙었을 것이다.

**남은 결과** 자동 접근이 막힌 32곳은 앱 ID도 사람이 넣어야 한다. 스토어에서 앱을 찾아
주소의 `id` 뒤 숫자를 `hints.ios_app_id` 에 넣으면 된다.

**중간에 잡은 치명적 버그 하나** 처음엔 bundleId 가 도메인을 뒤집은 모양인지로 판정했는데,
등록 가능 도메인을 "뒤 두 라벨"로 계산했다. 한국 도메인은 대부분 `cgv.co.kr` 처럼 2단계라
전부 `co.kr` 이 되고, 뒤집으면 `kr.co` 가 되어 **모든 한국 앱이 모든 한국 사이트와 일치**했다.
CGV 에 롯데시네마 앱 ID 가 붙은 것을 보고 발견했다. `co.kr`·`or.kr`·`go.kr` 등을
공개 접미사로 처리해서 고쳤다. 근거가 강해 보이는 규칙일수록 반례로 먼저 때려 볼 것.

## D-20. 한국어는 번역하지 않고 따로 쓴다

**결정일** 2026-08-15 (운영자 지적)

운영자 지적: "영어를 구글번역기로 돌린 느낌. 다듬어져 있지 않다."

맞는 지적이고 원인도 분명했다. **영어를 먼저 쓰고 한국어를 옮겼기 때문에** 영어 문장 구조가
그대로 남았다. `<T en ko />` 로 두 언어를 나란히 두는 구조가 이 실수를 부추긴다.

**증상**
- 영어 `we` 를 그대로 옮긴 "우리는 그것을 지킵니다" — 한국어는 주어를 뺀다
- 영어 동명사를 옮긴 "~하는 것이 됩니다", "~인 것처럼"
- "당신의 카드" — 영어 `your` 의 흔적. 한국어에서는 거의 안 쓴다
- "측정 안 됨", "양식에 없음" — 뜻은 맞지만 화면에서 읽히는 말이 아니다

**규칙** `ko` 는 `en` 의 번역이 아니라 **같은 사실을 한국어로 새로 쓴 것**이다.
길이나 문장 수가 달라도 된다. 판단 기준은 하나 — **한국 사람이 쓴 것처럼 읽히는가.**

**용어도 함께 정리했다.** 화면에 개발 용어를 쓰지 않는다.
`시그널` → `항목` · `측정` → `확인` · `프로브가 본 것` → `수집한 원본` ·
`커뮤니티 제보` → `이용자 제보` · `값 없음` → `기록 없음`

## D-21. 제보 창구를 우리 사이트로 옮긴다 — 정적 내보내기를 포기하면서

**결정일** 2026-08-15 (운영자 결정)

**문제** 제보를 GitHub 이슈 폼으로만 받고 있었다. 그러려면 제보자가 GitHub 계정을 만들고
로그인해야 한다. 한국을 여행 중인 외국인에게 그건 벽이고, **제보가 유일한 데이터원인

운영자 표현: "제보할 사람은 깃헙 로그인도 해야하고 필요없다고 해도 가독성도 떨어지고 불편함."

**한 것** 폼을 사이트 안(`/report`)에 두고, 서버 함수 `/api/report` 가 제보자 대신
이슈를 만든다. **뒤쪽(수집 → 집계 → PR 승인)은 한 줄도 바뀌지 않았다.**
이슈 본문 형식과 라벨을 기존 파서가 읽던 그대로 맞췄기 때문이다.

**포기한 것: `output: 'export'`**

D-11 에서 "서버 0대"를 위해 순수 정적 파일로 뽑고 있었다. Next 는 정적 내보내기와
서버 함수를 같이 쓸 수 없다. 둘 중 하나를 골라야 했다.

| | |
|---|---|
| 잃은 것 | '어디에나 올릴 수 있는 파일'이라는 성질. 실제로 옮길 계획은 없었다 |
| 지킨 것 | 비용 0원과 운영 부담 0 — 원칙의 진짜 목적 |

페이지 115개는 여전히 전부 빌드 시점에 미리 그려져 CDN 에서 나가고, 함수가 도는 것은
제보 한 건당 한 번뿐이다 (월 수십 회 예상). 공개 JSON API(`public/api/`)도 그대로 정적 파일이다.

Cloudflare Workers 도 검토했다. 정적 내보내기를 지킬 수 있지만 계정·CLI·대시보드가
하나씩 더 늘어난다. 운영자가 직접 코딩하지 않는 조건에서 관리할 곳을 늘리는 비용이
정적 파일이라는 성질보다 크다고 봤다.

**개인정보는 오히려 더 안전해졌다 (절대규칙 2)**

| | |
|---|---|
| 전 | 제보자가 GitHub 에 직접 글을 올린다 → 개인정보가 **공개 이슈에 먼저 뜨고** 우리가 수집 단계에서 거른다. 이미 공개된 뒤다 |
| 후 | `/api/report` 가 GitHub 에 올리기 **전에** 검사한다. 걸리면 이슈가 아예 만들어지지 않는다 |

같은 정규식이 `site/lib/screen.ts` 와 `src/lib/reports.ts` 양쪽에 있다.
중복이 아니라 의도된 이중 방어다. 고칠 때 반드시 양쪽을 같이 고칠 것.

**스팸** Turnstile 같은 외부 스크립트를 붙이지 않았다. 사이트가 외부 요청을 하나도
하지 않는다는 성질(추적 없음)을 지키기 위해서다. 대신 세 가지로 막는다 —
보이지 않는 미끼 칸, 제출까지 걸린 시간(2.5초 미만은 거부), 값의 형식 검사.
그래도 스팸이 오면 그때 Turnstile 을 붙인다. PR 승인 관문이 있어 사이트에는 못 올라간다.

**배포 설정이 바뀐다** 함수를 배포하려면 Vercel 이 `site/` 를 앱 루트로 알아야 한다.
루트 `vercel.json` 의 우회 설정(D-13)을 없애고 **Root Directory 를 `site` 로** 지정하는 것이
정석이다. 설정이 바뀌기 전 빌드는 실패하지만, Vercel 은 마지막 성공 배포를 그대로
서비스하므로 사이트가 내려가지는 않는다.

## D-22. 해외 접속은 (서비스 × 측정 지점)의 속성이다

**결정일** 2026-08-16

**문제** GitHub 러너가 매번 다른 지역에 뜬다. 2026-08-15 하루에만 다섯 곳에서 쟀다.

```
kr·Gyeonggi-do → us·Washington → us·Illinois → us·California → united kingdom
```

그때마다 값이 뒤집혔다. `overseas_access` 변경 22건 중 5개 서비스가 두 번 이상
뒤집혔고 전부 은행·인프라였다 — 서울교통공사·예스24티켓·KT·농협·신한은행.
가장 뚜렷한 사례는 정부·은행 아홉 곳이 Washington 에서는 열리고 Illinois 에서는
응답하지 않은 것이다.

**진짜 원인은 노이즈가 아니라 모델링 오류였다.** 이 값을 서비스 하나에 붙은 값으로
저장하고 "정답"이라고 불렀는데, 실제로는 **어디서 재느냐에 따라 달라지는 값**이다.
값 하나로 뭉개면 그날 관측한 가장 중요한 사실이 사라진다.

**한 것 둘**

1. **지점별로 남긴다.** `evidence.by_vantage` 에 지점마다 마지막 결과를 쌓는다.
   화면에서는 갈릴 때만 보여준다 — "어디서 확인했느냐에 따라 답이 갈립니다.
   us·California: 됨 · us·Illinois: 응답 없음".
   뭉개서 숨기던 것이 이제 그 자체로 사실이 된다.

2. **같은 지점끼리만 비교한다.** 이 지점에서 재 본 적이 없으면 비교할 대상이 없으므로
   변경으로 세지 않는다. 지점이 옮겨가서 생긴 차이는 "서비스가 바뀌었다"가 아니다.

**대가** 세계적으로 새로 막힌 서비스가 있어도 **같은 지점을 다시 방문할 때까지**
변경으로 잡히지 않는다. 값 자체는 그날 바로 갱신되므로 화면은 최신이고,
늦는 것은 `/changes` 기록뿐이다. 가짜 변경으로 이력을 채우는 것보다 낫다고 봤다.

**안 한 것** 여러 지점에서 재고 다수결을 내는 방법도 있었다. 정확도는 오르지만
실행 시간이 지점 수만큼 배로 늘고, 무료 한도(월 2,000분) 안에서 하루 1회를 지키려면
서비스 수를 줄여야 한다. 커버리지를 깎아서 정밀도를 사는 거래는 하지 않는다.
